# REFACTOR.md — Checkout Settings Module

## Summary

The checkout-settings module manages widget behavior, intervention policies, trigger rules, and handoff configuration. The module is well-structured with clean entity validation and optimistic concurrency control (If-Match). However, two operational bugs (PUT 500 error under concurrent updates, and missing ETag header on GET) impair reliability and DX.

## Findings

### CRITICAL

#### CSS-C1 — PUT /checkout-settings returns 500 on concurrent updates (no conflict recovery)

- **File:** `application/checkout-settings.use-cases.ts` (`UpdateCheckoutSettingsUseCase.execute()`)
- **Category:** Error Handling / User Experience
- **Description:** The use-case calls `repository.save(..., expectedUpdatedAt)` with optimistic concurrency. The Prisma repo's `updateMany` counts result rows: if `count !== 1`, it throws `OptimisticConcurrencyError()`. However, the controller does NOT catch this error; it bubbles to the global exception filter as a 500. The client receives no hint that this is a transient conflict, not a server failure.
- **Impact:** Concurrent edits fail with 500; merchants think the API is broken. They retry with stale data, causing a cascade of failures.\n- **Remediation:** Controller must catch `OptimisticConcurrencyError` and map it to `409 Conflict` with the current settings in the response. Client re-fetches and merges/retries. Add a `@Catch(OptimisticConcurrencyError)` exception filter or handle in the controller's try-catch.

#### CSS-C2 — GET /checkout-settings does not set ETag header

- **File:** `presentation/http/checkout-settings.controller.ts` (`get()` method)
- **Category:** API Contract / Caching\n- **Description:** The controller calls `this.entityTags.set(response, settings)` in `update()` and `reset()`, but NOT in `get()`. The GET response has no `ETag` header. When the client receives settings, it cannot use them as the `if-match` value for PUT because the header is missing from GET.\n- **Impact:** Clients must store the raw settings snapshot and re-POST them with PUT to get the ETag. Broken workflow.\n- **Remediation:** Call `this.entityTags.set(response, settings)` in `get()` before returning.\n\n---\n\n### HIGH\n\n#### CSS-H1 — Entity validation allows empty trigger list\n\n- **File:** `domain/entities/checkout-settings.entity.ts` (`validate()`)\n- **Category:** Domain Invariant\n- **Description:** `validateTriggers()` only checks for unknown triggers and duplicates. It does NOT enforce that at least one trigger is enabled. A merchant could update to `triggerRules: []` and the widget would never activate.\n- **Impact:** Silent misconfiguration; checkout never triggered.\n- **Remediation:** Add validation: `if (!rules.some(r => r.enabled)) throw new Error(\"at_least_one_trigger_required\")`.\n\n#### CSS-H2 — Handoff configuration not validated\n\n- **File:** `domain/entities/checkout-settings.entity.ts`\n- **Category:** Domain Invariant / Safety\n- **Description:** `handoff` object (message, channels) is not validated. A merchant can set `message: \"\"` or `channels: []` and it persists. At runtime, the agent receives an empty message.\n- **Impact:** Broken handoff UX.\n- **Remediation:** Validate in entity: `assertValidHandoffMessage(handoff.message)`, `assertNonEmptyChannels(handoff.channels)`.\n\n#### CSS-H3 — DTO validation does not match entity bounds\n\n- **File:** `presentation/http/checkout-settings.controller.ts` (no DTO file exists)\n- **Category:** API Contract / Validation\n- **Description:** The controller accepts `@Body() body: CheckoutSettingsPatch` with no class-validator decorators (it's from @zyon/shared-types). This means the API layer does not validate bounds before the entity layer; invalid data reaches the domain and triggers an exception instead of a 400.\n- **Impact:** Poor error messages; 500 instead of 400 for bad input.\n- **Remediation:** Create a dedicated DTO with class-validator rules (max intervention count, min cooldown, etc.) that mirrors entity bounds.\n\n#### CSS-H4 — CheckoutSettingsEntity.update() does not validate suppressionRules.blockedRegions\n\n- **File:** `domain/entities/checkout-settings.entity.ts` (`update()` method)\n- **Category:** Incompleteness\n- **Description:** The method spreads `suppressionRules` from the patch, but does not validate the `blockedRegions` array format. A merchant can inject invalid region codes.\n- **Impact:** Suppression rules are silently ignored at runtime.\n- **Remediation:** Add validation for region codes (e.g., ISO 3166 format).\n\n#### CSS-H5 — No upper bound on interventionPolicy.minimumAbandonmentScore updates\n\n- **File:** `domain/entities/checkout-settings.entity.ts` (`validate()`)\n- **Category:** Bounds Checking\n- **Description:** The entity validates `0 <= minimumAbandonmentScore <= 1`, but the DTO `CheckoutSettingsPatch` does NOT enforce this bounds. The API accepts `{ interventionPolicy: { minimumAbandonmentScore: 1.5 } }` and the entity rejects it with an exception (500).\n- **Impact:** Validation errors surface as 500s, not 400s.\n- **Remediation:** Create a DTO with `@Min(0) @Max(1)` decorators.\n\n---\n\n### MEDIUM\n\n#### CSS-M1 — Entity validation throws Error instead of domain exception\n\n- **File:** `domain/entities/checkout-settings.entity.ts` (`validate()` and helper functions)\n- **Category:** Error Contract / Consistency\n- **Description:** All validation errors are generic `Error(\"error_code\")` instead of domain exception classes (e.g., `InvalidCheckoutSettingsError`). This makes it hard to catch and recover from specific validation failures.\n- **Remediation:** Define `CheckoutSettingValidationError extends Error` with a `code` field. Rethrow in the use-case as `BadRequestException`.\n\n#### CSS-M2 — InMemoryRepository does not implement optimistic concurrency\n\n- **File:** `infrastructure/in-memory-checkout-settings.repository.ts`\n- **Category:** Test Double Fidelity\n- **Description:** The test double stores settings in a `Map` and implements the optimistic lock (compares `expectedUpdatedAt`), but it uses JavaScript timestamps which may not match Prisma's `Date` serialization. Tests may pass in-memory but fail in production.\n- **Remediation:** Use ISO string timestamps consistently in both repos. Add a contract test that verifies both implementations throw `OptimisticConcurrencyError` on the same conflict scenario.\n\n#### CSS-M3 — CheckoutSettingsEntity.update() mutates props in-place\n\n- **File:** `domain/entities/checkout-settings.entity.ts` (`update()` method)\n- **Category:** Immutability\n- **Description:** The constructor is private and the entity stores `props` as a private field, so mutation is encapsulated. However, `update()` mutates `this.snapshot.steps[field]` before returning a new entity. If the caller holds a reference to the old entity, they see stale state.\n- **Impact:** Subtle bugs in concurrent scenarios (unlikely but possible).\n- **Remediation:** Guarantee immutability: `return new CheckoutSettingsEntity({ ...this.props, ...updates })` instead of mutating in-place.\n\n#### CSS-M4 — No way to clear suppressionRules.blockedRegions\n\n- **File:** `application/checkout-settings.use-cases.ts`\n- **Category:** API Semantics\n- **Description:** The `update()` method spreads the current suppressionRules and then the patch. If a merchant sends `suppressionRules: { blockedRegions: [] }`, the update preserves the old value: `[...old, ...empty]` resolves to the old list.\n- **Impact:** Merchants cannot clear blocked regions via PATCH.\n- **Remediation:** Distinguish between \"omitted\" and \"explicitly empty\". If the patch includes `blockedRegions: []`, use it. If it's omitted, preserve current.\n\n#### CSS-M5 — EntityTagService integration is not tested\n\n- **File:** `presentation/http/checkout-settings.controller.ts`\n- **Category:** Test Coverage\n- **Description:** The controller calls `this.entityTags.set()` and `this.entityTags.assertIfMatch()`, but there are no unit tests verifying ETag round-trips or conflict scenarios.\n- **Remediation:** Add regression tests for: GET returns ETag, PUT with valid ETag succeeds, PUT with stale ETag returns 409, PUT without If-Match succeeds.\n\n---\n\n## Coupling Map\n\n```\ncheckout-settings\n  ← integrations/TenantAccessModule (for API key auth)\n  ← shared/http (EntityTagService, OptimisticConcurrencyError)\n  → no outbound dependencies ✓\n```\n\nDependencies are appropriate (infrastructure only).\n\n---\n\n## Proposed Changes\n\n1. **Add DTO validation** with min/max bounds for all scalar fields\n2. **Map OptimisticConcurrencyError to 409 Conflict** in controller or exception filter\n3. **Set ETag on GET** responses\n4. **Validate trigger rules** (at least one enabled, valid channel names)\n5. **Validate handoff** (non-empty message, valid channels)\n6. **Validate suppressionRules** (region codes, allow-clear semantics)\n7. **Add domain exception types** (CheckoutSettingValidationError)\n8. **Add contract tests** for both repository implementations\n9. **Document PATCH semantics** for nested objects (omitted vs. explicitly empty)\n\n---\n\n## SOLID Alignment\n\n- **SRP:** Entity validates; use-case orchestrates; repo persists.
